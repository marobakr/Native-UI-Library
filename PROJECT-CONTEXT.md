# Project Context

## Project Overview

**Name:** Vodafone Egypt Native UI Library  
**Purpose:** Framework-independent web component library for Liferay and other CMS platforms  
**Status:** Initialization - Ready for Component Development  
**Repository:** Native UI Library (this repo)  
**Reference:** Angular UI Library (`https://github.com/Mohamed-Adel-Web/vf-UI-components.git`)

## Project Goals

### Primary Goals
1. Convert Angular UI components to native web components
2. Maintain visual design consistency with Angular library
3. Ensure WCAG 2.1 AA accessibility compliance
4. Support RTL/LTR for multilingual contexts
5. Provide seamless Liferay integration

### Non-Goals
- This is NOT a port of Angular code
- This is NOT dependent on Angular or any framework
- This is NOT copying the Angular implementation line-by-line
- This is NOT tied to Liferay (integration is separate layer)

## Key Decisions

### Architectural Decisions

#### Decision 1: HTML-First Architecture
**Date:** 2026-09-20  
**Status:** Approved  
**Decision:** Component structure must be explicit in HTML, not generated by JavaScript

**Rationale:**
- Clearer separation of concerns
- Better maintainability
- Easier to understand and debug
- Framework-independent approach
- Works with server-side rendering
- Liferay can populate content directly

**Impact:**
- HTML templates contain full component structure
- JavaScript only enhances, doesn't create
- Components work even if JavaScript fails to load

#### Decision 2: Design Token-Driven Styling
**Date:** 2026-09-20  
**Status:** Approved  
**Decision:** All visual properties use CSS custom properties (design tokens)

**Rationale:**
- Consistent design across components
- Easy theming and customization
- Liferay can override tokens for site-specific styles
- Future-proof for design system evolution
- No hard-coded values

**Impact:**
- All colors, spacing, typography use tokens
- Easy to adapt for different Vodafone markets
- Theme customization without code changes

#### Decision 3: CMS Independence
**Date:** 2026-09-20  
**Status:** Approved  
**Decision:** Core library has no Liferay dependencies; integration is separate

**Rationale:**
- Library can be used in any environment
- Easier to test and develop
- Cleaner architecture
- Portable across CMS platforms
- Liferay-specific code isolated in integration layer

**Impact:**
- No FreeMarker syntax in component source
- No Liferay APIs in component code
- Liferay integration via fragments and themes
- Library can be used outside Liferay

#### Decision 4: Progressive Enhancement
**Date:** 2026-09-20  
**Status:** Approved  
**Decision:** Components work without JavaScript, enhanced with JavaScript

**Rationale:**
- Better accessibility
- Works in low-bandwidth environments
- Resilient to JavaScript errors
- SEO-friendly
- Server-side rendering compatible

**Impact:**
- Core functionality in HTML/CSS
- JavaScript adds interactions
- Graceful degradation

### Technology Decisions

#### Decision 5: Modern JavaScript (ES6+)
**Date:** 2026-09-20  
**Status:** Approved  
**Decision:** Use modern JavaScript without transpilation for legacy browsers

**Rationale:**
- Modern browsers support ES6+
- Cleaner, more maintainable code
- No build complexity for JavaScript
- Better performance
- Target browsers: Chrome 90+, Firefox 88+, Safari 14+

**Impact:**
- ES6 modules
- Classes
- Arrow functions
- Template literals
- Async/await
- Optional chaining

#### Decision 6: CSS Custom Properties (Native CSS)
**Date:** 2026-09-20  
**Status:** Approved  
**Decision:** Use native CSS custom properties, not preprocessors

**Rationale:**
- No build step for CSS
- Runtime theming possible
- Simpler toolchain
- Better Liferay integration
- Modern browser support sufficient

**Impact:**
- No SCSS/Less
- Design tokens as CSS custom properties
- CSS nesting if needed (modern browsers)

#### Decision 7: Minimal Dependencies
**Date:** 2026-09-20  
**Status:** Approved  
**Decision:** Keep external dependencies to absolute minimum

**Rationale:**
- Smaller bundle size
- Fewer security vulnerabilities
- Less maintenance overhead
- Better long-term stability

**Impact:**
- No UI frameworks (React, Vue, etc.)
- No utility libraries unless critical
- Standard Web APIs preferred

### Testing Decisions

#### Decision 8: Vitest for Testing
**Date:** 2026-09-20  
**Status:** Approved  
**Decision:** Use Vitest as the test runner

**Rationale:**
- Fast and modern
- Great ESM support
- Compatible with Vite
- Good developer experience

**Impact:**
- Tests use Vitest syntax
- Coverage with c8/v8
- Fast test execution

### Process Decisions

#### Decision 9: GitHub Copilot as Primary Development Tool
**Date:** 2026-09-20  
**Status:** Approved  
**Decision:** GitHub Copilot will perform actual development work

**Rationale:**
- Cursor used only for initialization
- GitHub Copilot will handle component conversion
- Custom agent and prompts designed for Copilot

**Impact:**
- All prompts and instructions target Copilot
- Agent designed for Copilot chat
- Skills optimized for Copilot workflow

#### Decision 10: Component-by-Component Conversion
**Date:** 2026-09-20  
**Status:** Approved  
**Decision:** Convert components incrementally, not all at once

**Rationale:**
- Allows learning and iteration
- Easier to validate quality
- Can deliver incrementally
- Reduces risk

**Impact:**
- Priority-based conversion order
- Each component fully tested before next
- Can deploy partial library

## Angular Library Reference

**Repository:** `https://github.com/Mohamed-Adel-Web/vf-UI-components.git`  
**Status:** READ ONLY - Design reference only  
**Usage:** Analyze for design, structure, and behavior patterns

### What to Extract from Angular Library
- Visual design (colors, spacing, typography)
- Component structure (layout, hierarchy)
- Variants and states
- Behavior patterns (interactions, state management)
- Accessibility patterns (ARIA, keyboard nav)
- Design tokens
- Responsive behavior
- RTL/LTR support

### What NOT to Extract
- Angular-specific code
- TypeScript decorators
- Angular templates syntax
- Angular services/dependency injection
- Angular module system

## Conversion Workflow

```
Discovery → Analysis → Conversion → Validation → Integration
```

### Phase 1: Discovery
- Explore Angular library
- Identify components
- Extract design tokens
- Plan conversion roadmap

### Phase 2: Analysis
- Deep dive into specific component
- Document structure, props, events
- Document accessibility patterns
- Plan native implementation

### Phase 3: Conversion

- Implement CSS styles
- Implement JavaScript behavior
- Write tests
- Create documentation

### Phase 4: Validation
- Code quality review
- Functionality testing
- Visual testing
- Accessibility testing
- Performance testing
- Cross-browser testing

### Phase 5: Integration (Future)
- Create Liferay fragments
- Document integration patterns
- Provide usage examples

- Accessibility tests pass

- README complete
- Usage examples provided
- API documented
- Accessibility notes included

## Important Notes

### For Future Developers

**This is a native reimplementation, not a translation.**
- Don't copy Angular code
- Understand the design, recreate natively
- HTML structure must be explicit
- Use design tokens for all styling
- Progressive enhancement philosophy

**The Angular library is READ ONLY.**
- Never clone into this repository
- Never modify the Angular library
- Use it as design reference only

**Keep it simple.**
- Avoid unnecessary abstractions
- Use standard Web APIs
- Minimal dependencies
- Clean, readable code

### For Liferay Developers

**The library is CMS-independent.**
- Core components have no Liferay code
- Integration happens in fragments
- Liferay-specific logic in fragments only
- Library can be used in any environment

### For GitHub Copilot

**Follow the agent and skills.**
- Use `@native-ui-engineer` agent
- Reference instructions and prompts
- Use skills for guidance
- Follow the established patterns

**Quality over speed.**
- Take time to understand components
- Don't rush conversions
- Validate thoroughly
- Document completely
